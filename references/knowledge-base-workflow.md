# 知识库工作流

用于读取和更新主流程已经定位的 `<私人知识库>`。目录边界只由 `<私人知识库>/Home.md` 规定；元数据只帮助检索和维护，不能替代正文范围与来源关系。

## 一、进入条件与根目录

只有用户明确要求读取、保存、整理、更新、沉淀或继续已有内容，或者当前交付物本身就是持久文件时，才进入知识库流程。普通解释、研究和实践默认在当前回复完成。

先运行 `python scripts/private_library.py show` 取得唯一根目录，再读取 `<私人知识库>/Home.md`。配置或 `Home.md` 缺失时，当前任务仍可使用用户材料和外部来源继续；结果必须保存到本机时，只询问可用知识库位置。

## 二、查找已有主题

从当前问题提取主题名、真实别名、缩写和必要的中英文术语。先查 `10-Knowledge` 文件名，再查正文：

```powershell
rg --files "<私人知识库>/10-Knowledge" | rg -i "关键词1|关键词2|English term"
rg -n -i -g "*.md" "关键词1|关键词2|English term" "<私人知识库>/10-Knowledge"
```

优先打开标题、`topic` 或 `aliases` 直接命中的文档，再根据开头的主题范围、正文内容、状态和更新时间判断是否相关。需要核对证据或恢复原始上下文时，沿链接读取 `20-Sources`；涉及正在进行的工作、长期领域或最终成果时，再读取对应的 `30-Projects`、`50-Areas`、`40-Outputs` 或 `60-Systems`。

本地资料存在关键缺口、已经过时或需要当前事实时，再扩大到外部搜索。文本命中只提供候选，必须阅读全文后判断。

## 三、保持一个主题一个活动真源

写入前再次搜索主题与别名，并比较候选实际回答的问题：

- 处理同一个问题、机制或判断边界：更新现有文档。
- 新材料只是证据、案例、限制或子问题：合并到现有文档的对应位置。
- 能独立回答另一个长期问题，而且边界与现有主题不同：新建主题文档，并链接上位或相邻主题。
- 多个专题需要共同入口：更新最接近的综合主题文档。

同一主题只保留一份活动文档。历史变化由版本管理、项目记录和正文中的必要说明承担，不创建“新版”“整理版”或日期副本。

## 四、按内容作用落位

| 内容 | 正式位置 | 写入方式 |
| --- | --- | --- |
| 网页、书籍、论文、字幕、访谈和其它原始材料 | `20-Sources` | 保存出处、来源角色、版本和必要上下文；只有本地材料或获得保留授权时写入完整原文 |
| 已消化的概念、机制、证据判断、适用边界和可复用案例 | `10-Knowledge` | 合并进唯一主题文档，并把来源放在对应主张附近 |
| 有明确目标和结束条件的研究、学习或实践 | `30-Projects` | 保存范围、状态、材料链接、缺口和下一步 |
| 已确认完成的研究、实践或其它成果 | `40-Outputs` | 保存最终版本，并链接实际使用的知识和项目 |
| 没有固定结束日期的长期责任领域 | `50-Areas` | 保存当前状态、维护边界和相关知识入口 |
| 可重复使用的流程、模板和工作规则 | `60-Systems` | 只保存跨任务稳定的方法，不复制具体主题正文 |

暂时无法判断归属的材料进入 `00-Inbox`；停用但仍需保留的内容移入 `90-Archive`。

早期版本的私人库可能含有写作案例、钩子、写作输出和写作系统。这些目录不属于当前工作流，本 Skill 不读取、不初始化、不验证、不移动，也不把它们合并进当前知识结构。

## 五、区分来源和知识

来源文档回答“这个来源实际提供了什么”，保留作者、时间、入口、版本、必要上下文和缺失边界。主题知识文档回答“当前足够可靠的认识是什么”，保留机制、证据判断、适用范围、冲突、开放问题和实践反馈。

重要来源放在它支撑、限制或反驳的主张旁边。来源冲突会改变结论时保留双方、各自条件和当前判断。为了教学构造的例子标明解释作用，不能冒充来源事实。

抽象、技术或公式密集的主题可以在同一正式文档中保留两个层次：先用现实问题和普通语言建立理解，再保存精确定义、公式、成立条件和必要关系。两层服务同一主题，不拆成互相竞争的活动文档。

## 六、完整材料的覆盖

如果用户要求沉淀整节课、整篇论文、整本短材料或另一份完整来源，写入前根据材料分析阶段识别核心知识单元，并逐项确定它进入哪个现有主题、新主题或综合入口。

综合主题负责呈现全局问题、单元关系和学习路径；足够独立且深入的单元可以形成专题，由综合入口说明关系。来源文档负责忠实记录材料范围、结构和缺失边界。写后确认每个核心单元已经得到最小解释，或者能够从综合入口直接进入对应专题。

用户只要求一个概念或片段时，以该范围为覆盖单位，不把局部沉淀扩成整份材料工程。

## 七、写入与写后核对

正式修改前重新读取目标文件，避免基于旧版本覆盖用户修改。一次任务需要更新多个文件时，先确定全部准确目标与内容，再逐一写入并逐一重读。

1. 需要长期保留的新来源先写入或更新 `20-Sources`。
2. 把新结论、修正、关系、边界和开放问题合并进 `10-Knowledge` 的唯一主题文档。
3. 新关系会改变导航或上位模型时，更新相应综合主题并说明关系。
4. 任务属于持续项目、长期领域或正式成果时，更新对应状态和知识链接。
5. 更新必要日期，确认活动目录中只有一份正式主题文档。
6. 重新读取每个写入文件，检查标题、主题范围、来源链接、重要边界和内部链接。
7. 本地来源要求哈希时，从实际写入文件重新计算并与记录值比较。
8. 告诉用户实际更新了哪些文件、知识和关系。

正文直接写入确认后的唯一正式文件。`private_library.py show` 返回 `marktree_cli` 不改变默认写入方式；普通任务不调用 `scripts/marktree_integration.py`。只有用户明确要求使用 Marktree、读取其变更或通过它同步时，才进入该工具的检查与同步流程。

## 八、完成标准

- 读取和写入使用同一个已确认私人库根目录。
- 同一主题没有新增平行活动版本。
- 来源、知识、项目和成果按各自作用落位并相互链接。
- 写后重新读取了真实文件，用户能够找到并继续使用结果。
- 写作职责退出后留下的旧目录没有被触碰或重新接入。
