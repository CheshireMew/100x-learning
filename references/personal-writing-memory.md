# 个人写作记忆

用于在用户要求以本人声音写作、延续既有作品、检查是否重复表达，或当前知识库已经配置长期写作声音时，分别读取可靠的声音证据和发布历史。它不负责提供本次事实，也不替代内容案例库。

## 什么时候进入

实际起草、改写或审查可发布内容时，满足任一条件就进入：

- 用户要求“像我”“延续我的写法”或引用自己的既有作品；
- 用户询问这个选题、观点、钩子、故事或资源组合以前是否写过；
- 当前知识库存在长期写作声音真源。

用户指定另一位作者、品牌或虚构角色时，以用户提供并允许使用的对应材料为准，不读取个人声音。没有声音档案或本人作品时，使用当前原话、有效正文和普通直接的表达继续写，不临时编造声音特征。

## 四类材料各自负责什么

- **当前材料**：提供本次写作任务的事实、立场、经历、链接和交付要求；同一对象在另一任务中的写法反馈不自动进入。
- **声音真源**：保存已经确认的长期视角、推进、节奏、用词和表达边界。位置是 `<私人知识库>/60-Systems/Writing/style-guide/voice.md`。
- **发布历史**：索引已经发布或确认保存的正文，用于查重和判断内容增量。发布账号、发布网站和确认终稿只证明这篇内容进入过发布历史，不证明它由用户亲自写成。
- **声音证据**：发布历史中另外标明写作来源并明确允许用于声音学习的正文。只有人工写作或经过充分人工改写、且 `voice_eligible: true` 的记录进入这一层。
- **内容案例库**：提供经过筛选的结构和表达方法。案例可能来自本人或外部作者，但“被选为案例”本身不能证明用户身份、经历、立场或个人声音。

同一作品只保留一个正文真源。发布历史、声音资格、声音档案和案例库不互相复制正文；同一原文可以有不同消费资格，但每种资格都由自己的明确字段决定。

案例文件中的社交原帖只有在规范发布入口匹配 `<私人知识库>/60-Systems/Writing/writing-memory.json` 中已经验证的账号时，才进入发布历史。账号匹配只生成发布归属；脚本再读取 `writing_origin` 和 `voice_eligible` 判断能否进入声音检索。缺少这两个字段时按 `unknown` 和 `false` 处理，不能从账号、目录、案例身份或已经发布反推声音资格。正文仍只读取“原帖全文”区块，`writing_format` 只确定成品形态。不能因为来源都是社交平台就把独立帖、产品帖和资源分享统一记成 `short-post`。

## 写作前的证据顺序

成品形态已经由上层确定，再按下面的顺序取得作者声音：

1. 用户在本次写作任务中的明确要求和原话；
2. 同一成品中由用户亲自提供的样稿，或用户明确要求按其声音保留的片段；
3. 长期声音真源；
4. 成品形态和内容职责相同、并且明确具有声音资格的作品；
5. 其它明确具有声音资格的本人作品；
6. 通用写作原则与内容案例。

当前要求可以改变本次写法，但不会自动改写长期声音。发布历史只证明内容出现过；声音证据只帮助判断怎样表达，文中的旧事实和旧结论都不能代替本轮材料。

同一成品的当前有效正文继续承担改写对象和版本真源，但不会整篇自动成为声音样本。Agent 或 AI 起草的部分即使已经发布、进入当前版本或被用户要求继续修改，也只有用户明确指出要保留其声音时才提供对应表达特征；用户亲自改写、替换或明确评价的部分，按用户实际确认的范围提供本次声音证据。

这里的“本次写作任务”由上层已经锁定的成品和连续修改链决定，不等于整段会话。另一 Skill 的研究回答、另一篇内容及其用户反馈，即使讨论同一个项目，也不能自动成为当前作者声音、核心含义、固定开头或措辞偏好；用户明确把其中某段作为本次声音样本或写作要求移交时，才按指定角色使用。旧回答不能因为写得像用户认可的版本就替换当前可写材料，也不能成为成稿事实核查的依据。

## 检索声音证据

使用 `scripts/writing_memory.py search --purpose voice`。声音检索必须传入已经确定的成品形态；已经确定内容职责时同时传入 `--content-type`。这条路径不接收主题查询，产品名、行业名和其它题材词不参与声音排序：

```powershell
python scripts/writing_memory.py search --purpose voice --format original --content-type "个人观察与实测" --limit 3
python scripts/writing_memory.py search --purpose voice --format product --content-type "项目与产品介绍" --limit 3
```

支持的成品形态是：

- `original`：脱离上下文也能成立的独立帖；
- `quote`：引用原帖并增加判断或机制；
- `resource`：说明资源为什么值得使用以及怎样使用；
- `thread`：多条内容持续推进一个问题；
- `product`：用结果、场景、机制或取舍介绍产品；
- `short-post`：没有指定更具体成品形态的通用短帖；
- `article`：完整文章或文章大纲。

检索结果只负责召回具有声音资格的候选。选择一至三篇内容职责相同或最接近的作品，读取本地正文，比较视角、判断力度、推进、节奏和自然毛边。一个旧句只在一篇样本中出现时，把它视为那次内容的具体表达；不拆取其中的感叹、转场、排名外壳、条件句或 CTA 句型拼进新稿。可复用的声音特征需要得到长期声音真源、用户当前明确要求或多个可靠样本的共同支持。用户明确要求仿写某一篇时，才按当前任务指定的强度使用单篇结构。

没有同形态、同职责的声音证据时，使用长期声音真源、当前用户语言和普通直接的表达继续写。其它形态的作品不再作为自动回退；用户明确要求扩大声音分析时才另行读取，并且不让它规定本次长度、上下文依赖和结尾。

## 检查内容是否重复

个人发布历史存在时，起草前使用 `scripts/writing_memory.py search --purpose novelty`，用主题和核心主张检索；用户明确要求查重时，再用完整草稿复查：

```powershell
python scripts/writing_memory.py search --purpose novelty --query "AI 写作工具怎样减少上下文切换" --format original --limit 3
python scripts/writing_memory.py search --purpose novelty --query-file "draft.md" --format thread --limit 3
```

主题词只在这条路径里帮助寻找旧内容。命中的记录无论由人还是 AI 写成都可以证明“以前发布过什么”，但不能因此进入作者声音。逐项比较：

- 开头在承诺什么；
- 核心主张是否相同；
- 使用了哪个故事、经历或资源组合；
- 依赖什么证据、结果或机制；
- 文章怎样推进；
- 最后落在哪里。

只是长期观点相同不构成重复。新内容至少应带来一项会改变读者理解的增量，例如新证据、不同机制、实际进展、新的适用场景或新的个人判断。只有换词、重排句子或更换表面例子时，继续寻找新材料或缩小到本次真正新增的部分；没有新增内容就直接告诉用户，不制造一篇近义改写。

## 维护发布记录

普通写作只读，不写入知识库。上层已经确认用户要求保存、确认终稿或记录已发布内容时，把唯一正文写入 `40-Outputs/Writing`，并使用以下 frontmatter 让它进入本人写作记录：

```yaml
---
type: writing-output
status: final
updated: YYYY-MM-DD
author: 作者名
source: user-confirmed
format: article
content_type: 内容类型
writing_origin: human-edited
voice_eligible: true
published_url: ""
---
```

`source` 在实际状态成立时使用 `user-confirmed`、`published-article`、`published-post` 或 `published-thread`。`format` 使用本文件列出的成品形态。已经发布时填写规范入口；尚未发布时保留空值。`writing_origin` 使用 `human`、`human-edited`、`ai-generated`、`curated`、`translated` 或 `unknown`。只有用户明确确认文字能代表自己的表达时才填写 `voice_eligible: true`；它只允许与 `human` 或 `human-edited` 同时出现。

本人发布内容同时保存为社交案例时，在案例的隐藏索引中使用同一套形态名称：

```markdown
<!-- content-case-index
writing_format: "product"
writing_origin: "human-edited"
voice_eligible: true
index_task: "……"
index_topics: ["……"]
index_moves: ["……"]
-->
```

`writing_format` 缺失或不在支持列表中时，发布记录校验失败并要求修正源文件，不猜测，也不降级成 `short-post`。规范发布入口可以在缺少声音字段时进入发布历史，但会以 `writing_origin: unknown`、`voice_eligible: false` 保存。

保存正文后运行：

```powershell
python scripts/writing_memory.py build-index
python scripts/writing_memory.py validate
```

索引写到 `<私人知识库>/60-Systems/Writing/published-content-index.jsonl`，保存相对私人库的正文路径、成品形态、发布归属、写作来源、声音资格、日期和正文哈希。相同发布入口或完全相同正文会合并，`40-Outputs` 中的当前终稿优先于来源归档；声音资格跟随最终正文自身，不从被合并的旧版本继承。社交平台状态链接能够提供发布日期时，由脚本从规范 ID 恢复日期；无法可靠确定时保持未标注。

长期声音只在用户明确认可，或多个可靠本人样本反复出现同一特征时更新。新样本只重复已知特征、没有改变既有判断时，保持声音真源不变。

## 完成位置

分别完成声音选择与查重后，把声音真源、稳定声音特征和内容增量判断交回上层。两条检索结果不能互相代用。实际写作把声音证据与其它材料一起放入上下文；需要写作说明时，只用自然语言说明声音来源和成稿影响，不记录检索分数、候选状态或隐藏推理。用户明确要求查重或声音分析时，再说明重复发生在哪里以及本次怎样形成真实增量。
