# 个人写作记忆

用于在用户要求以本人声音写作、延续既有作品、检查是否重复表达，或当前知识库已经配置长期写作声音时，读取可靠的本人写作证据。它不负责提供本次事实，也不替代内容案例库。

## 什么时候进入

实际起草、改写或审查可发布内容时，满足任一条件就进入：

- 用户要求“像我”“延续我的写法”或引用自己的既有作品；
- 用户询问这个选题、观点、钩子、故事或资源组合以前是否写过；
- 当前知识库存在长期写作声音真源。

用户指定另一位作者、品牌或虚构角色时，以用户提供并允许使用的对应材料为准，不读取个人声音。没有声音档案或本人作品时，使用当前原话、有效正文和普通直接的表达继续写，不临时编造声音特征。

## 四类材料各自负责什么

- **当前材料**：提供本次事实、立场、经历、链接和交付要求。
- **声音真源**：保存已经确认的长期视角、推进、节奏、用词和表达边界。当前知识库的默认位置是 `System Knowledge/60-Systems/Writing/style-guide/voice.md`。
- **本人写作记录**：索引用户确认稿和已发布正文，用于寻找同形态样本、判断近期用法和检查内容重复。正文仍只保存在 `40-Outputs` 或经过身份核验的来源目录，索引不复制正文。
- **内容案例库**：提供经过筛选的结构和表达方法。案例可能来自本人或外部作者，但“被选为案例”本身不能证明用户身份、经历、立场或个人声音。

同一作品只保留一个正文真源。发布记录、声音档案和案例库不互相收录对方的正文。

案例文件中的社交原帖只有在规范发布入口匹配 `System Knowledge/60-Systems/Writing/writing-memory.json` 中已经验证的本人账号时，才同时进入本人写作记录。索引只读取“原帖全文”区块，不读取文件末尾隐藏的 `content-case-index`；未验证账号和没有规范入口的案例只保留案例角色。

## 写作前的证据顺序

成品形态已经由上层确定，再按下面的顺序取得作者声音：

1. 用户本轮明确要求和原话；
2. 当前有效正文或用户确认稿；
3. 长期声音真源；
4. 最近且成品形态相同的本人确认稿或已发布内容；
5. 其它本人作品；
6. 通用写作原则与内容案例。

当前要求可以改变本次写法，但不会自动改写长期声音。本人作品只证明作者怎样表达，文中的旧事实和旧结论不能代替本轮材料。

## 检索同形态作品

使用 `scripts/writing_memory.py search`。查询由当前主题、核心主张和最有辨识度的对象组成；已经确定成品形态时传入 `--format`：

```powershell
python scripts/writing_memory.py search --query "AI 写作工具怎样减少上下文切换" --format original --limit 3
python scripts/writing_memory.py search --query-file "draft.md" --format thread --limit 3
```

支持的成品形态是：

- `original`：脱离上下文也能成立的独立帖；
- `reply`：依赖原帖语境的回复；
- `quote`：引用原帖并增加判断或机制；
- `resource`：说明资源为什么值得使用以及怎样使用；
- `thread`：多条内容持续推进一个问题；
- `product`：用结果、场景、机制或取舍介绍产品；
- `short-post`：平台未细分时的通用短帖；
- `article`：完整文章；
- `newsletter`：Newsletter 正文。

检索结果只负责召回候选。选择一至三篇最接近的同形态作品，读取其本地正文，判断当前真正需要沿用的视角、推进、节奏和自然毛边。没有同形态作品时先使用长期声音真源和当前材料；确实还需要其它本人证据时，可以再检索 `short-post` 或 `article`，但明确把它当作较低优先级的其它形态，不用它规定本次长度、上下文依赖和结尾。

## 检查内容是否重复

个人发布记录存在时，起草前用主题和核心主张做一次检索；用户明确要求查重时，再用完整草稿复查。逐项比较：

- 开头在承诺什么；
- 核心主张是否相同；
- 使用了哪个故事、经历或资源组合；
- 依赖什么证据、结果或机制；
- 文章怎样推进；
- 最后落在哪里。

只是长期观点相同不构成重复。新内容至少应带来一项会改变读者理解的增量，例如新证据、不同机制、实际进展、新的适用场景或新的个人判断。只有换词、重排句子或更换表面例子时，继续寻找新材料或缩小到本次真正新增的部分；没有新增内容就直接告诉用户，不制造一篇近义改写。

## 维护发布记录

普通写作只读，不写入知识库。上层已经确认用户要求保存、确认终稿或记录已发布内容时，把唯一正文写入 `40-Outputs/Writing`，并使用以下 frontmatter 让它进入本人写作记录：

```yaml
---
type: writing-output
status: final
updated: YYYY-MM-DD
author: 作者名
source: user-confirmed
format: article
content_type: 内容类型
published_url: ""
---
```

`source` 在实际状态成立时使用 `user-confirmed`、`published-article`、`published-newsletter`、`published-post` 或 `published-thread`。`format` 使用本文件列出的成品形态。已经发布时填写规范入口；尚未发布时保留空值。

保存正文后运行：

```powershell
python scripts/writing_memory.py build-index
python scripts/writing_memory.py validate
```

索引默认写到 `System Knowledge/60-Systems/Writing/published-content-index.jsonl`，只保存路径、成品形态、来源、日期和正文哈希。相同发布入口或完全相同正文会合并，`40-Outputs` 中的用户确认终稿优先于来源归档。社交平台状态链接能够提供发布日期时，由脚本从规范 ID 恢复日期；无法可靠确定时保持未标注。

长期声音只在用户明确认可，或多个可靠本人样本反复出现同一特征时更新。新样本只重复已知特征、没有改变既有判断时，保持声音真源不变。

## 完成位置

取得足够的声音与新鲜度证据后，把声音真源、实际采用的本人作品、声音特征和新鲜度判断交回上层写作阶段。实际写作的调查信息可以列出采用的来源和本稿真正沿用的特征，但不展示检索分数、未采用候选的详细比较或隐藏推理；用户明确要求查重或声音分析时，再说明重复发生在哪里以及本次怎样形成真实增量。
