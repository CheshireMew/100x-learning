# GitHub 项目清单模板

用于盘点、推荐、排名或列出多个 GitHub 项目，帮助读者按同一标准看出每项适合谁、能带来什么结果以及从哪里访问。本模板不负责把一个项目完整讲成独立介绍。

## 进入与停止

上层已经选定“GitHub 项目清单”时进入，并提供这次是推荐清单、资源合集、排名还是锐评。项目数量和成品形态已经在进入本模板前确定，本模板不把清单改成多个单项目介绍。

清单已经覆盖入选项目、统一选择标准、每项最有用的差异和真实入口，并按用户要求完成收束时停止。

## 先确定选择标准

上层已经根据清单服务的读者、用途和表达任务完成写作前联网研究，并交来候选、统一标准和精选材料。本模板确认：

- 清单服务哪类读者和哪个具体用途；
- 项目为什么能够放在同一组比较；
- 入选和排序使用什么统一标准；
- 每项最能改变读者选择的结果或适用场景；
- 哪些项目因为证据不足、不符合标准或与主题无关而不入选；
- 用户是否要求 star 数、费用、平台、技术栈或其它字段。

每个项目沿用材料包中确认的项目类别、主要用途、直接动作和作用对象。清单的统一问题可以突出这些事实支持的结果或使用场景，但不能把不同项目重新命名成来源和真实用法中不存在的宽泛任务。

用户要求排名或锐评时，排序和评价必须能够回到同一个标准。只要求罗列资源时不制造胜负。

每个入选项目只消费能够说明其角色、结果、适用对象、选择依据和真实入口的精选材料。

## 项目事实

每个入选项目至少核对项目名、真实入口、主要用途、适用对象和本清单要强调的结果。star 数、当前维护状态、费用和版本属于实时信息；只有用户给出的格式需要，或它们会改变读者选择时才核查并写入。

项目方的速度、质量和领先程度保留声明身份。没有足够事实说明项目适合谁或带来什么结果时，不用宣传词补空白。

## 专项模板

用户给出参考格式时，逐项沿用字段顺序、换行、链接位置、Markdown 包装和装饰符号。没有另给格式时使用：

```text
[根据读者问题和清单价值写一至两句自然开头]

1. 项目名（只有需要时才写 star 数）
一句话说明最能改变选择的结果或适用场景
项目链接

[其余项目]

[根据清单用途自然收束；存在真实下一步时给出入口]
```

每项默认使用一个完整句子回答同一个读者问题，同时保留项目之间真正不同的角色。材料确实需要补充条件、取舍或比较时可以增加一句，不为了整齐压掉会改变选择的信息。

开头可以直接说明这份清单解决什么选择，也可以从目标读者的真实问题、期待、代价或意外发现进入。用户要求广泛传播时，上层必须独立检索钩子库并在有多个结果时比较候选；成稿从选中钩子的原句替换事实位置，保留材料能够承担的句子关系、进入动作和承接方式。结果、问题、场景、代价、冲突、反差、意外或规模都可以成为开头，具体选择由清单材料已有的关系决定，不强制使用判断、反差或固定句式。

结尾落在整体选择、真实下一步或已经形成的余味。读者确实需要尝试、收藏、继续查看或等待后续时再给出对应动作。

完整成稿按上层统一交付格式放进代码块；模板、案例、钩子、声音和事实来源调查信息留在代码块外。标题符号、加粗和分隔线只在用户给出的格式中出现。

## 使用案例和作者声音

上层显式检索 `short` 完整案例，用统一选择关系、读者变化和希望采用的表达特征寻找候选；“清单与资源推荐”只作为提高排序的线索，不排除写法更合适的其它短内容。选中前把案例开头和主要推进需要的关系映射到本轮清单材料，核心关系缺失就查看下一篇。选中后阅读全文，让真正贴合的案例帮助判断清单怎样开头、排序、保持信息密度和收束；作者材料决定判断力度、称呼、幽默和自然毛边。完整案例和开头参考分别选择，完整案例的开头不能替代病毒式内容的独立钩子检索。

案例中的项目、star 数、排序和评价都属于当时内容，不能进入新清单。本轮项目事实、统一标准和作者当前判断决定最终内容。

## 交付前检查

- 单项目介绍和项目清单没有混用模板。
- 所有项目符合本轮统一标准，排序或评价有明确依据。
- 每项都说明最能改变读者选择的结果、角色或适用场景。
- 项目事实和入口真实；实时字段在交付前完成核查。
- 每个项目的类别、主要用途和直接动作没有被统一开头改写成虚构任务。
- 病毒式传播的首句和承接句能够对回所选钩子原文；无法对应时没有声称“沿用”。
- 多个项目没有机械复制同一句型，也没有为了变化而损坏统一比较标准。
- 用户参考格式、Markdown 包装、链接位置和结尾要求得到保留。
