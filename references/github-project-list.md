# GitHub 项目清单模板

用于盘点、推荐、排名或列出多个 GitHub 项目，帮助读者按同一标准看出每项适合谁、能带来什么结果以及从哪里访问。本模板不负责把一个项目完整讲成独立介绍。

## 进入与停止

上层已经选定“GitHub 项目清单”时进入，并提供这次是推荐清单、资源合集、排名还是锐评。项目数量和成品形态已经在进入本模板前确定，本模板不把清单改成多个单项目介绍。

清单已经覆盖入选项目、统一选择标准、每项最有用的差异和真实入口，并按用户要求完成收束时停止。

## 先确定选择标准

上层已经根据清单服务的读者、用途和表达任务完成素材发现与净化，并交来候选、统一标准和可写材料。本模板确认：

- 清单服务哪类读者和哪个具体用途；
- 项目为什么能够放在同一组比较；
- 入选和排序使用什么统一标准；
- 每项最能改变读者选择的结果或适用场景；
- 哪些项目因为现有材料无法写出明确价值、不符合标准或与主题无关而不入选；
- 用户是否要求 star 数、费用、平台、技术栈或其它字段。

每个项目只接收材料包中真正服务清单的对象身份、主要用途、直接动作和作用对象，不把只供备查的平台、限制和技术细节一起交给写作者。这些内容不要求每一项使用同一种类别句或介绍顺序，也不能被统一开头改写成毫无根据的宽泛任务。

用户要求排名或锐评时，排序和评价必须能够回到同一个标准。只要求罗列资源时不制造胜负。

每个入选项目只消费能够说明其角色、结果、适用对象、选择依据和真实入口的精选材料。

## 写作材料与成稿核查

起草前只保留能说明项目角色、结果、适用对象、选择依据和入口的材料，不逐项核对项目名之外的完整资料。star 数、当前维护状态、费用、版本、许可证和平台只有用户格式需要或确实改变选择时才进入草稿；进入之后再由统一成稿核查处理。

现有材料无法让一个项目的作用变得具体时，宁可不选或少写，不用官方宣传词补空白。口语概括和有力度的判断可以先服务成稿，只有会改变项目核心能力、比较结果或读者行动的说法才在成稿后收窄。

## 专项模板

用户给出参考格式时，逐项沿用字段顺序、换行、链接位置、Markdown 包装和装饰符号。没有另给格式时使用：

```text
[根据读者问题和清单价值写一至两句自然开头]

1. 项目名（只有需要时才写 star 数）
一句话说明最能改变选择的结果或适用场景
项目链接

[其余项目]

[根据清单用途自然收束；存在真实下一步时给出入口]
```

每项默认使用一个完整句子回答同一个读者问题，同时保留项目之间真正不同的角色。材料确实需要补充条件、取舍或比较时可以增加一句，不为了整齐压掉会改变选择的信息。

开头可以直接说明这份清单解决什么选择，也可以从目标读者的真实问题、期待、代价或意外发现进入。完整案例与钩子技巧分别从各自目录定位，多份相关原文一起进入创作上下文。结果、问题、场景、代价、冲突、反差、意外或规模都可以提供启发，具体开头由清单材料、作者声音和所有参考共同决定，不强制固定句式，也不要求选出唯一钩子。

结尾落在整体选择、真实下一步或已经形成的余味。读者确实需要尝试、收藏、继续查看或等待后续时再给出对应动作。

完整成稿由上层直接交付；需要写作说明时，用自然语言说明材料来源、参考方向和重要取舍，并列出实际阅读的完整案例与钩子路径，不建立执行记录。标题符号、加粗和分隔线只在用户给出的格式中出现。

## 使用案例和作者声音

上层浏览完整短内容与独立钩子目录，围绕统一选择关系、读者变化和希望获得的表达方向打开多份有差异的原文。相关全文共同进入写作上下文，可以同时影响清单的开头、排序、信息密度和收束；不能拼成新模板或改变信息预算。普通写作不要求与案例逐项或逐段对应，用户明确要求仿写时才近距离适配。作者材料决定判断力度、称呼、幽默和自然毛边。

案例中的项目、star 数、排序和评价都属于当时内容，不能直接搬进新清单。本轮材料、统一标准和作者当前判断决定最终内容，成稿实际使用的关键说法再统一核查。

## 交付前检查

- 单项目介绍和项目清单没有混用模板。
- 所有项目符合本轮统一标准，排序或评价有明确依据。
- 每项都说明最能改变读者选择的结果、角色或适用场景。
- 成稿实际使用的项目身份、入口和实时字段在交付前完成核查，没有为了核查补入免责声明。
- 每个项目的类别、主要用途和直接动作没有被统一开头改写成虚构任务。
- 多个相关完整案例与多个钩子示例的原文已经共同进入创作上下文，没有唯一参考、固定数量和采用审计。
- 开头由当前清单材料支持，并由后文兑现。
- 多个项目没有机械复制同一句型，也没有为了变化而损坏统一比较标准。
- 用户参考格式、Markdown 包装、链接位置和结尾要求得到保留。
