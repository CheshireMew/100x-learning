# 写作前素材发现与净化

这个阶段只负责两件事：发现能增加内容表现力的材料，并把没有写作价值的信息挡在创作上下文之外。它不替模型决定角度、主线、开头、结构和结尾，也不在动笔前执行成稿核查。用户已经给出的内容主次继续保持：重点可以影响选材，只要求提到或带到的信息只作为配角材料，搜索不会把它升级成主线。

新写、扩写和实质重组默认进入。只改错字、格式或做等义压缩，或者用户明确只用给定材料时，不额外联网。用户要求研究、判断或事实核查时，另走研究路线；研究结果里真正适合公开表达的部分再进入本阶段。

## 发现有用材料

先打开用户给出的对象、页面或材料，确认没有认错主题并看见主要内容。随后按任务需要浏览官网、仓库、文档、演示、媒体、KOL、创作者、真实用户、Issue、Discussion、论坛和社区讨论，寻找能够增加以下任一内容的原文与上下文：

- 具体动作、结果、演示、前后变化和使用瞬间；
- 人们如何描述问题、收益、比较、替代选择和意外反应；
- 比官方定位更自然、更容易被读者理解或转述的说法；
- 会改变选材、叙述视角或读者关系的争议、案例和必要解释。

GitHub 项目可以组合项目名与 `demo`、`review`、`use case`、`tried`、`alternative`、体验、实测、对比、Issue、Discussion，以及 Reddit、Hacker News、X、YouTube、Bilibili 等来源词。搜索结果只用于发现入口，实际采用前打开原文或完整上下文。新来源不再增加场景、细节、比较或说法时停止，不按固定数量凑资料。

只有当前成品确实需要行动入口、安装步骤、报名时间、价格、兼容性或提示词时，才额外寻找对应信息。它们不是普通介绍的默认材料。

## 剔除没有写作价值的内容

搜索得到的是候选，不是必须全部交给模型的资料包。保留真正可能影响本篇内容或写法的动作、结果、场景、演示、比较、反应、原话和少量必要解释。用户要求逐字保留的内容直接保留；只要求提到或带到的内容保留足够准确表达它的部分，不连同完整解释一起放大。

下列内容在与当前成品无关时留在来源页，不进入创作上下文：

- 官方套话、完整功能表、路线图和重复说明；
- 通用免责声明、保守提醒、风险罗列和为了显得全面而添加的背景；
- 边缘功能、内部实现、无关限制和只供备查的技术字段；
- 搜索过程、来源等级、排除理由、候选评分和事实核查清单。

研究、比较和核实阶段使用的治理过程、许可证判断、技术验证、反方材料与保守边界，默认只影响是否采用和怎样表达。用户没有要求展开，而且它们不会改变当前读者的理解或行动时，留在内部依据中；用户只要求带到结论时，只把结论按原有内容关系交给成文。

价格、许可证、平台、兼容性、API Key、硬件、版本和运行条件不是一律删除，也不是一律保留：用户正在评估它们，或者缺少它们会让当前成品的主要行动失真时才进入写作材料。相应来源链接保留在任务内部，等草稿实际使用相关说法后再按需复查。

字幕、访谈和会议记录先恢复谁在回应什么、前后说法如何变化以及出现了什么结果，再提取相关片段；不要把时间切片顺序当成正文结构。

## 交给模型的材料包

最终只把以下内容交给成文阶段：

- 用户要求、已经确定的内容主次和必须保留的内容；
- 净化后的当前对象材料及必要上下文；
- 当前成品确实需要的行动、利益、时间或技术信息。

来源链接和核查依据继续留在任务内部，不与创作材料混成一份提示。专项模板、完整案例、独立钩子与按需取得的作者声音由上层另行加入。模型看到完整材料后自行决定讲什么、怎样开头、怎样推进和在哪里结束。
