# 单个 GitHub 项目介绍

用于在成文前保留单个 GitHub 项目介绍特有的事实边界。本文件只准备材料，文件正文、栏目和说明不进入成文输入。

写作准备材料应保留项目的官方定位、完整能力范围，以及实际有用的演示、动作、结果、场景、比较、用户反应和自然说法。项目主页、安装方式、运行条件、价格、许可证、平台或提示词只在用户要求或正文确实需要时加入。

项目身份由官方定位与真实能力共同支撑，不能用某个快速示例或单项能力重新定义整个项目。

不要把 README 机械压缩成功能摘要，也不要预先排除具体功能；一个功能确实最能帮助读者理解项目时可以成为主要内容。架构、工作流、文件格式和内部术语只有在能帮助理解或行动时才进入正文。

用户没有指定开发背景时，不假定读者已经理解依赖、虚拟环境、锁文件、缓存、CLI 或同类开发术语。先用一个可见过程说明项目做成了什么，例如从一台新电脑、一个空目录或一份现有代码开始，最后得到可以运行、修改或交付的结果；需要保留的术语随后用它实际替读者完成的动作解释。“依赖”写成项目需要的软件包，“虚拟环境”写成给每个项目单独准备的运行环境，“锁文件”写成记住所用软件的准确版本，“缓存”写成复用已经下载的文件；读者不需要搜索或操作原词时，只写自然中文。用户没有要求教程时，不罗列命令、竞品工具名、操作系统或安装条件证明项目很强；一个主要结果和最能证明它的一项事实已经足够。项目统一替代多套旧工具时，直接写过去要在多个工具之间切换，不逐个报名字。不能把一串功能名或工具名当作项目价值。

面向普通读者的非教程短帖，除项目名、读者需要识别的领域名和一个确有必要的比较对象外，不保留实现语言、命令名、竞品名单或操作系统名单；这些信息存在于 README 不等于值得进入正文。草稿完成后只留一个主要结果和一项最强证据，删掉为了展示能力完整度而追加的功能与兼容信息。

吸引人的项目短内容先比较材料中的具体利益、可见结果、真实场景、异常细节、自然语言调用、命令和数字，选择没读过 README 的目标读者也能立刻看懂价值的一项开场。项目名称和准确类别可以直接说，但不必固定放在第二句；真实输入或命令只有不熟悉语法的目标读者也能从中看出用途和结果时才承担开头，否则放到项目价值已经讲清之后。可见结果能够直接说清时，直接写结果，不先补一个较弱的中间产物再否定它制造反差。

钩子已经写出主结果或利益时，正文可以用 `P24 结果证据展开` 补充不同维度的能力、数量、格式或范围；以输入或命令开场时，可以用 `P01 输入—处理—输出` 继续说明工作流。命令示例已经承担开头时，正文不再复述同一句输入。

普通介绍可以保留一个有用入口；安装、运行或教程请求可以使用相应命令。安装、配置和能够运行是不同状态，来源没有把它们等同时不能用“安装后就能运行”代替；短帖可以用“配置好后”概括必要设置已经完成，不必因此罗列平台兼容表。准备完成后只把项目原始事实和必要上下文并入材料。草稿中的实时数据和行动条件回到对应来源核对。
