# 单个 GitHub 项目介绍

用于在成文前保留单个 GitHub 项目介绍特有的事实边界。本文件只准备材料，文件正文、栏目和说明不进入成文输入。

写作准备材料应保留项目的官方定位、完整能力范围，以及实际有用的演示、动作、结果、场景、比较、用户反应和自然说法。项目主页、安装方式、运行条件、价格、许可证、平台或提示词只在用户要求或正文确实需要时加入。

项目身份由官方定位与真实能力共同支撑，不能用某个快速示例或单项能力重新定义整个项目。

不要把 README 机械压缩成功能摘要，也不要预先排除具体功能；一个功能确实最能帮助读者理解项目时可以成为主要内容。架构、工作流、文件格式和内部术语只有在能帮助理解或行动时才进入正文。

吸引人的项目短内容先比较材料中的具体利益、可见结果、自然语言调用、命令、异常细节、数字和真实场景，选择最能让读者立刻看懂价值的一项开场。项目名称和准确类别可以直接说，但不必固定放在第二句；项目介绍也可以用一句真实输入或命令开头。可见结果能够直接说清时，直接写结果，不先补一个较弱的中间产物再否定它制造反差。

钩子已经写出主结果或利益时，正文可以用 `P24 结果证据展开` 补充不同维度的能力、数量、格式或范围；以输入或命令开场时，可以用 `P01 输入—处理—输出` 继续说明工作流。命令示例已经承担开头时，正文不再复述同一句输入。

普通介绍可以保留一个有用入口；安装、运行或教程请求可以使用相应命令。安装、配置和能够运行是不同状态，来源没有把它们等同时不能用“安装后就能运行”代替；短帖可以用“配置好后”概括必要设置已经完成，不必因此罗列平台兼容表。准备完成后只把项目原始事实和必要上下文并入材料。草稿中的实时数据和行动条件回到对应来源核对。
