# 单个 GitHub 项目介绍

用于把一个 GitHub 项目写成普通读者能直接看懂、愿意停留和转述的独立短内容。本文件只负责成品身份，直接消费上层已经净化的写作材料，不重新搜索、核查项目或规定固定正文骨架。

## 写作输入

上层应当同时提供：

- 从官方仓库、文档、演示、媒体、KOL、创作者、真实用户或社区讨论中筛出的可写材料；
- 本篇最值得传播的一项变化、能够把它写具体的动作或结果，以及需要时的项目入口；
- 目标读者、作者位置和可用声音；
- 多个完整案例全文、多个钩子来源示例和对应文件路径。

写作输入已经去掉无关功能、边缘限制、官方免责声明和通用保守提醒。模型直接从留下的动作、结果、演示、比较和自然说法中选择讲法，不在本模板里重新建立官方事实底座。

## 找到真正值得传播的关系

不要把 README 压缩成一段介绍。先从全部材料中找到一个最容易让目标读者停下来的真实关系，例如：

- 一个熟悉输入直接变成了可见结果；
- 原本分散、麻烦或昂贵的动作变得简单；
- 演示出现了普通人一眼能看懂的意外结果；
- 项目与常见工具存在会改变选择的真实差异；
- 创作者或用户说出了比官方定位更自然的使用价值；
- 当前事件、争议、反应或转折让项目此刻值得谈。

传播力来自关系本身和语言力度，不来自夸张形容词。材料只有项目功能时，就把功能写成具体动作和结果；材料确实有反应、比较、矛盾或惊喜时，可以把它们带进开头和推进。第一句提出的好奇、反差或判断必须由后文兑现。

## 正文怎样写

从当前材料、外部真实声音和所有创作参考中自由选择最自然的进入方式。可以从作者反应、一次接触动作、结果、场景、问题、演示、比较或判断开始，不固定为“结果开场—项目定位—能力—入口”，也不要求某篇案例承担某个位置。

面向普通读者时，前两句优先出现一项能够直接感受到的变化。读者如果还要把 MP4、时间线、工作流、组件或格式翻译成“这对我有什么用”，说明开头仍停在技术层，需要回到具体动作、使用场景或结果。项目名和身份在读者需要识别时自然出现，可以融入场景、结果或入口，不固定单独成句。

多个完整案例可以共同影响开头、推进、列点、节奏或收束；多个钩子示例也可以共同提供进入方式。模型不必挑一个模仿，不登记逐篇采用状态，也不为证明借鉴而改变成稿。只有用户明确要求仿写或续写某篇时，才近距离对应它的句段职责。

来源示例使用“我刷到”“我试了”“把材料丢进去”等第一人称时，可以借鉴接触动作和语气，不要求先证明叙事动作逐字发生过。具体使用时长、测试结果、数字和感受如果最终承担可信度，由成稿核查决定是否修正。

只写服务于主要传播关系的内容。README 里的能力清单、架构、文件格式和内部术语只有在能让读者更理解、更相信或知道下一步时才进入。外部报道和用户讨论同样按作用取舍，不为了显示研究充分而堆进正文。

项目入口放在读者自然需要访问的位置。结尾可以落在项目入口、已经建立的结果、作者判断或自然余味；内容已经说完就结束。

开源、许可证、平台、免费范围、付费依赖、API Key、硬件和运行条件只有在本篇确实值得读者知道时才出现；信息价值不够就省略，适合保留时可以压缩进项目入口附近或结尾，不单独插入一段。成稿使用了精确许可证、价格、平台或运行条件时，再核查对应说法。不再使用固定结尾，也不把“仓库可以访问”自动写成“100% 开源，完全免费”。

## 交付前回读

- 完全不了解该领域的读者能够说清项目直接帮他做什么。
- 开头来自当前项目的真实结果、反应、比较或场景，不是换个项目名也成立的官方套话。
- 前两句是具体动作或结果，不是工作流、格式和内部机制的堆叠。
- 搜索材料中的官方套话、通用提醒、无关平台和边缘限制没有进入正文。
- 媒体、KOL、创作者和用户材料确实改变了选材或表达，没有只把 README 换一种说法。
- 多个相关完整案例与多个钩子示例已经共同进入写作上下文，没有唯一参考和采用证明。
- 相邻句子没有换一种说法重复项目身份、核心价值或结果。
- 项目入口真实，结尾停在内容已经完成的位置。
- 成稿中会改变项目理解或读者行动的事实已经核查，口语概括和轻微泛化没有被机械修平。
