# 单个 GitHub 项目介绍

用于把一个 GitHub 项目写成可独立发布的短内容。本文件只说明这种成品需要让读者认识一个具体项目，不规定项目必须从哪个功能切入，也不规定开头、段落和结尾的位置合同。

## 专项输入

上层提供净化后的项目材料，包括项目的总定位与完整能力范围，以及真正有用的演示、动作、结果、场景、比较、反应和自然说法。多个完整案例与多个独立钩子原文一起进入共同成文。项目主页、安装方式、运行条件、价格、许可证、平台或提示词只在用户要求或当前成品确实需要时加入。

## 成品职责

成稿应让目标读者知道这是一个什么项目，以及它为什么值得此刻认识、尝试、讨论或转述。至于从能力、结果、使用场景、反差、演示、用户反应、观点还是其它细节切入，由模型根据材料和读者自行决定。

项目身份由官方总定位和完整能力范围共同支撑。快速开始、首个示例、单项能力、某段详细工作流或与竞品的一个差异只说明项目的一种用法；除非用户明确要求聚焦，不能用它们重新定义整个项目。用户只要求提到或带到的能力、致谢、边界与实现信息自然出现即可，不据此选择开头、主线或主要篇幅。

不要把 README 机械压缩成功能摘要，也不要因为“功能不是价值”而预先排除某个具体功能：如果一个功能本身最能让读者理解项目，它就可以成为主要内容。架构、工作流、文件格式、治理过程和内部术语只有在能帮助当前读者理解价值或采取行动时才进入正文；否则留在材料中，不能因为它们更容易证明严谨就挤占传播重点。

用户要求更有传播力时，让模型自由利用具体细节、冲突、反差、结果、意外感、语言张力和钩子参考，不强制先提炼唯一项目级关系或套固定传播公式。

普通介绍通常保留一个有用的项目入口；安装、运行或教程请求可以使用相应指南或命令。入口怎样出现由正文用途和用户格式决定，不要求固定最后一行。提示词只有在用户要求或正文的实际用途需要时出现。

草稿完成后统一交回上层处理实质错误和阅读问题，本模板不重复事实核查清单。
