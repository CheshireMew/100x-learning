# 单个 GitHub 项目介绍写作模板

用于把一个已经研究清楚的 GitHub 项目写成普通读者可以直接看懂、愿意继续读的独立短内容。本模板只负责写法，不负责研究项目、盘点源码、补齐功能、评价维护状态或列出使用条件。

## 进入与停止

上层已经选定“单个 GitHub 项目介绍”时进入，并提供这次是介绍、推荐、分享、续写、评测还是比较。项目数量和成品形态已经在进入本模板前确定，本模板不改成项目清单。

读者已经知道这个项目最特别的变化、它大致能帮谁做什么，并获得真实入口后立即收束。正文不因为 README 还有更多功能而继续展开。

## 写作输入

上层提供：

- 已经选定的表达任务；介绍、推荐或分享默认是正面介绍，评测和比较使用对应任务；
- 写作前联网研究交来的精选材料包；
- 已经从作者位置、目标读者、用户材料和精选网络材料想清的本次讲法；
- 当前读者、作者声音和发布要求；
- 已经核实的项目名、主要用途、经过真实使用信号筛选后最值得传播的变化、能把这项变化写具体的事实和真实入口；
- 实际用来比较、淘汰或重排传播点的选材依据，以及其中哪些材料会直接进入正文；
- 一条真正贴合的完整项目介绍案例；
- 实际采用的开头参考；
- 必须逐字保留的文字。

上层已经检查过材料支撑。仍发现关键缺口时，把具体缺口交回上层补充或收窄说法；本模板不自行研究，也不使用提醒、限制和无关功能填空。

写作前研究已经负责从社区反馈和真实用法中选出真正有人称赞、复述和比较的变化。正文从项目和这个变化本身开始。正面介绍只使用精选材料包中的正面结果、场景、社会证明、必要官方事实和入口；评测或比较使用上层为该任务选出的对应材料。

## 正文怎样写

1. **第一句先带动情绪。** 从当前材料里选择最能让目标读者产生好奇、兴奋、共鸣或意外的真实变化。第一句只负责把人带进来，下一句马上兑现。
2. **紧接着说出项目。** 用普通话说明项目名、它改变了什么，以及读者为什么会在意。读者不需要先懂项目类别、框架或内部实现。
3. **把完整案例的写法映射过来。** 逐句判断案例每句话怎样说、承担什么作用，再用当前项目的真实内容完成同样的推进。只要事实允许，近距离保留案例的具体说法、段落顺序、短句节奏、并列作用、信息密度和收束位置；某一句依赖当前项目没有的数字或关系时只改那一句，不把整篇重新写成普通说明文。正文先从当前材料挑选真正有力的事实、动作、结果或例子，再决定是一项、几项还是不用列表；案例影响它们放在哪里、怎样形成力度和节奏，不决定条目数量，也不要求补齐功能清单。
4. **入口放在固定结尾之前。** 项目链接、仓库名或用户要求保留的入口放在正文自然需要的位置。
5. **使用固定最后一句。** 正文最后一行永远逐字写：

```text
100% 开源，完全免费。
```

这句话之后不再添加链接、说明、提醒、CTA、表情或其它文字。

段落之间怎样推进、句子节奏、并列内容的位置和中间怎样转折，优先沿用已选完整案例中能够由当前事实承担的部分，再由作者声音做局部调整。段落数和列点数量由当前项目实际值得写的内容决定；没有事实需要时，不为了显得完整而添加场景、输入输出、工作流角色、能力数量、技术栈、权限、限制或风险。

直接引语、数字、日期、链接和明确归因按来源逐项对应。标题、钩子、类比、对照和判断由作者表达决定：用户已经给出或确认时优先沿用，用户没有指定时根据作者位置、读者认知和材料支持的关系选择；它没有声称逐字复述某个来源时，不因来源使用了另一个表面名称而机械改回。

## 案例与开头参考

完整案例是正文的主要写作示范，不是只供提取一个标签的灵感。它的题材和类型只负责帮助检索；选中后从完整原文学习句段职责、措辞、节奏、格式、情绪推进和收束。它的开头已经适合当前项目时，同一案例可以同时作为开头参考，不必再找一条独立开头案例。

需要另一种情绪或开头技巧时，再使用开头案例。开头参考只提供技巧和情绪作用，完整案例继续决定正文怎样推进；两者都不能提供本次项目事实和作者身份。

## 交付前检查

- 第一行已经带动目标读者的真实情绪，下一句立即交代项目和变化。
- 完全不了解该领域的读者不需要先读术语解释，就能复述项目最特别的地方。
- 正文能够与所列完整案例逐段对应，并实际保留当前事实支持的表达、节奏和格式；不是只借了一个痛点概念。
- 项目事实的数量和段落数来自当前材料，没有为了复现案例表面形状硬凑或删减内容。
- 每项正文事实都服务同一个主要变化，没有从研究材料补成技术说明。
- 选材研究已经影响最主要的变化和事实顺序，但研究过程与无关意见没有代替项目本身成为开场。
- 项目入口真实，并且位于固定最后一句之前。
- 正文最后一句严格等于“100% 开源，完全免费。”，其后没有任何内容。
