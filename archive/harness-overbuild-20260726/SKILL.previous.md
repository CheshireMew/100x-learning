# 100x Learning

<!-- 2026-07-26：旧 Harness 架构退出活动 Skill，保留此文件仅供人工恢复。 -->

## 目标与边界

把材料、陌生主题或真实学习任务转化为用户当前真正用得上的知识，并在用户需要时继续形成可分享内容候选、独立短内容、文章、实践产物或长期知识。目标、实践方式和写作参与程度由用户决定；Agent 负责降低资料处理与表达成本，让学习围绕理解和使用展开。

适用于：

- 从字幕、文章、课程、访谈、书摘或其他长材料中找主线、高价值片段和关键概念。
- 从视频、书籍、文章、访谈或课程中识别普通受众也能理解、感兴趣或实际受益的内容，并整理核心主张、必要语境、支撑材料、来源状态和可用素材。
- 把已经整理和核实的学习或研究成果写成能够独立成立的短帖、Thread、短文案、文章或 Newsletter。
- 从 GitHub 项目的官方介绍、用户提供的源码研究结果或已经确认的项目事实中，提炼普通人能立即理解的用途与能力，写成简短项目介绍；同一系列中的项目继续说明彼此关系并沿用已确认的呈现方式。
- 主动研究主题、判断来源、拆解概念、比较相近认识或解决具体理解卡点。
- 围绕真实材料或任务诊断怎么学，并选择能够产生可观察结果的方法。
- 把本次学习或研究用于模拟、分析、判断、工具、方案、长期知识或文章。

相邻请求的路由：

- 翻译、校对、转写、格式清洗和普通压缩摘要由语言或文档处理流程完成。
- 普通代写、营销文案和作业答案使用对应写作流程。
- 基于现成条件直接生成计划、清单、日程或操作方案时，使用相应领域的执行流程。

“计划”“方案”和“写作”承接本次学习、研究、知识迁移或真实经历时进入本 Skill，其余情况按交付目标进入相邻流程。

分享候选识别负责判断什么内容值得传播、准确定位、说明普通受众价值，并整理后续成文或制作所需的内容真源。独立短帖、Thread、短文案、文章和 Newsletter 继续在本 Skill 成文；图文卡片、GIF、视频、音频或播客交给 `visual-multimedia` 选择载体并制作。

独立短帖、Thread、短文案、文章和 Newsletter 由当前 Agent 直接起草和修改。Agent 先完成材料读取、研究和事实核查，再按 `references/content-writing.md` 把内容真源、当前作者声音、对应写作模板与同类型完整案例合并成唯一生产输入。短内容读取 `short` 全文，文章或 Newsletter 读取 `article` 全文；用户明确要求病毒式传播时，在对应正文案例之外同时读取 `hook`。作者声音始终来自用户本轮原话、当前有效正文、确认稿、已发布文字或维护中的声音档案，并直接决定用词、句长、重复、判断力度、幽默和自然毛边。GitHub 项目短介绍同时读取 `references/github-project-short-content.md` 和“项目与产品介绍”完整案例。内容选材、知识讲解、研究材料、写作大纲、声音分析和内容审计继续由对应流程完成。只有用户明确点名外部模型时才调用该模型；模型不可用不改变默认成文流程。

## 开始前的最小判断

开始研究、解释、实践或写作前，只确定会改变执行方式的信息：

1. **当前用途与目标表现**：快速看懂、形成判断、筛选分享候选、准备短内容或文章、完成实践或深入研究；最终需要识别、回忆、解释、执行、辨别、保持还是迁移。
2. **交付物、对象、版本与位置**：重点片段、分享候选清单、内容真源交接包、短帖、Thread、短文案、文章、Newsletter、概念讲解、研究材料、实践产物或修改意见；同时确定交付针对的对象、原始材料版本、作者身份与确认状态、聊天回答、Markdown 文件或现有成果位置。执行工具、分析来源和写作对象分别确认。
3. **授权范围**：选材、文章起草、声音分析、内容审计、研究、事实核查、知识库写入和实际发布分别按本轮授权启用。
4. **已有上下文**：用户提供的材料、已有知识、知识库、真实环境和项目规则。
5. **必要时才判断的信息**：信息性质、已有基础和学习卡点；只有方法选择会改变结果时才展开。

简单任务只判断前三项。用户已经说清时直接执行；缺失信息只影响局部时从现有材料推断。只有缺口会改变大部分产物、现实风险、验收标准或保存位置时，先读取材料和项目规则，仍无法确定再询问一个关键约束。

写作任务在读取材料和形成内容包前，先锁定唯一写作对象、用户本轮要求的表达角度和按优先级排列的核心信息。对象依次从用户明确点名、用户提供的文件或仓库、当前对话持续讨论的主题和当前工作目录中确认。用户明确给出的主张和角度保持最高叙事优先级，来源材料补充使其成立的事实、机制和必要边界，辅助事实始终围绕同一主线组织。多个合理对象会产生不同正文时，只询问对象这一项。

写作对象和核心信息锁定后，把本次工作转成写作任务、内容类型、少量主题词、所需结构和交付形态，再进入本地案例检索。唯一活动索引按钩子、完整短内容、完整文章及内容类型组织，不按作者分库；检索器先锁定正文内容类型，再按 `writing_task`、`topics` 与 `structure` 排序，并把本地全文、说明和适用场景直接交给当前 Agent。每次成文都读取对应模板与同类型完整正文案例；用户明确要求病毒式传播时再加入开头案例。案例库缺少所需资产时，先补齐经过来源确认的同类全文，再进入成文。

GitHub 项目短介绍先锁定项目身份、官方或已确认来源、读者要记住的用户结果、项目间关系和本轮呈现合同。当前用户指令、当前有效作者文字、用户提供的风格样稿和同一系列中已经确认的正文依次决定开头作用、篇幅、正文形态、emoji、链接与结尾。完成这些判断后直接进入专项流程；当前用户原话至少作为一项作者声音来源，已有确认稿、发布稿或声音档案时继续补充。

写作任务在询问作者声音或个人经历缺口前，依次读取用户当前提供的草稿或原话、用户确认稿、已发布文章和唯一声音真源，随后检索已有项目、`40-Outputs`、`20-Sources` 的文章索引及其实际正文。当前指令和本轮删改决定写作目标、内容取舍与需要修正的层级；真实用户文本提供个人经历和高置信声音证据，声音真源可以吸收外部案例中可迁移的结构机制。Agent 草稿保持待修改状态，用户明确保留或确认的部分可以成为当前正文的有效来源。材料足以决定本轮表达时直接使用；仍缺少会改变主体的经历、立场或高保真声音时再询问一个关键输入。

每次成文都建立 `author_voice`。`sources` 记录用户本轮原话、当前有效正文、确认稿、已发布文字和维护中的声音档案；`signals` 提取一至五项当前最有用的词汇、句长、节奏、重复、判断力度、幽默或完成度；`preserved_choices` 记录用户明确保留的称呼、原句、重复和结尾。作者材料与当前指令共同决定正文怎样说，内容真源与 `shareable_point` 决定这次讲什么。外部案例直接展示结构和表达机制，不提供用户身份、亲历、事实或立场。

每次用户跟进，先把本轮补充或纠正合并进当前仍有效的任务合同。用户没有撤回的交付形态、写作对象、表达角度、核心信息、受众、声音、平台、长度和授权继续生效；只重建新指令实际改变的部分。已有材料继续作为证据；用户明确更换对象、立场、交付载体、版本或授权时，再重做对应映射。

短内容的完整性按目标读者能否理解事件和核心判断衡量。事件型内容先整理行动者、动作、适用对象或条件、相较此前的变化，以及这项变化怎样支撑作者判断；正文只展开使这条因果链成立的事实。时间过程本身承载主线时才按时间线展开，其余时间点、组织沿革和系统细节保留在内容真源中。

先锁定本次学习的**范围单位**。用户说“看下一课”“看懂这篇文章”或提供完整材料要求学习时，范围单位是整份材料，后续追问只改变相关概念的解释深度。用户一开始只问某个概念或片段时，范围单位就是该概念或片段。用户明确调整范围时随之更新。

抽象、技术或公式密集的材料默认同时交付两个层次：

- **可理解层**先回答它在解决什么现实问题，用一个具体情境建立最小模型，并用普通语言连起原因和结果。
- **正式层**保留精确定义、正式术语、核心公式或结构、成立条件、概念关系和会改变使用方式的边界，只收纳当前主线需要的证明和板书。

可理解层始终在正式层之前，并说明正式表达对应前面例子的哪一部分。用户反馈“看不懂”“太抽象”或指出当前解释层次不合适时，从原材料和真实用途重新建立可理解层，同时保留仍然成立的正式内容。

两个层次的完整性按整份交付或整篇主题知识判断。用户要求“普通人总结”“实际怎么用”“行动建议”或类似低门槛收束时，该部分用已解释的普通语言写判断、动作、条件和可观察结果；正式定义、公式和高阶关系放在后续独立正式层。用户明确把本次范围缩成单一通俗产物时按新范围停止。

两层要求用于技术内容的讲解与知识沉淀。分发任务围绕目标受众判断原始内容是否可懂、有用、完整和值得传播；用户随后要求讲解或沉淀某个候选时，再对该主题交付可理解层与正式层。

解释被点名的核心概念时，可理解层用熟悉语言和一个完整情境回答三个问题：满足什么条件就称为这个概念，它具体拿什么信息来回答什么问题，以及它怎样起作用。比较两个相近概念时，让它们经过同一个情境，用同一维度说明差异，并给出至少一个只符合其中一方的例子。

用户问“某个现实对象是不是这个概念”时，先固定观察对象、时间尺度、已知信息和状态包含什么，再分别说明定义要求、模型假设和现实证据。模型结论只覆盖模型状态和被检验的统计量；其它历史信息与分布特征按现有证据判断。

### 深度与相关性

- **快速理解**：核心含义或来源、关键机制、一个具体情境和一项会直接造成误解的边界。
- **写作或判断**：在最小理解上补充真正支撑主张或选择的证据、故事、反方和实施差异。
- **深入研究**：仅在用户明确深究，或方法、数据与争议本身就是任务时展开来源谱系、冲突证据和细分边界。

输出由直接答案、会改变理解或选择的内容、必要前提和用户明确要求的信息组成。现有材料足以支持当前用途时停止搜索和展开。

### 准确性服从授权与影响

研究、事实核查或现实判断中的高影响主张需要核实；边缘术语、命名史、人物评价和传播轶事在会改变理解、选择、责任归属或许可证判断时研究。金融、医疗、法律和实时规则按当前任务核实关键事实；声音分析和结构修改仍按本轮授权范围交付。

先区分事实主张与口语、夸张和作者判断。口语与修辞保留表达力度；可能被读者当作确定事实、收益承诺或行动依据的内容使用短而可用的修正。

传播写作在内容真源范围内，选择一个具体、可证成、目标读者愿意复述的判断，再用决定性事实、机制或细节把它讲透。完整案例展示开头、推进、密度、节奏和收束怎样连在一起；真实作者材料决定当前正文的词汇、句长、重复、判断力度、幽默和完成度。每个重要句子承担项目特有事实、动作与结果、能够成立的作者判断、真实声音或理解与转述价值中的至少一项，每一段继续增加信息或推进判断。

## 共享原则

1. **目标属于用户，足够优先于完整**：先满足当前用途的最低成功标准，再停止；必要证据、反馈和边界随任务保留。
2. **方法服从任务**：根据目标表现、信息性质、已有知识和当前卡点选择结构、解释、检索、练习或实践。
3. **先搭最小模型，再进入正式结构**：先给主线、具体情境和关键关系，再提供当前主题必要的定义、公式、条件和边界；简化调整进入顺序和展开量，保留长期需要的进阶入口。
4. **反馈用于重新判断和修正**：用来源、例子、模拟、实际产物、样稿对比或低压力检索发现问题。用户纠正理解层次、范围或表达方式时，重判当前任务和有效约束，再从对应环节重建。
5. **来源按作用判断**：分别标记事实证据、方法依据、解释、案例、用户约束和素材；按来源质量决定证明力度，复制媒体前检查许可证与署名。
6. **材料与事实分别处理**：主张、证据、案例、推测、修辞和分析推断各自承担对应角色；事实核查由本轮授权触发。
7. **实践服务真实用途**：实践承接本次学习或研究，由用户的理解和使用目标决定进入时机。
8. **知识库保持唯一真源**：已有知识、来源、项目、成果和写作声音按各自角色落位；同一文章的用户确认稿或已发布版本成为活动成果，项目状态和链接同步迁移。
9. **写作使用经过验证的真实材料与当前授权**：Agent 草稿作为过程材料；第一人称经历来自当前用户原文、用户确认稿或已发布文章；外部案例只提供事实、结构和表达参考，不改写成用户亲历；个人文章保持用户的主体与文体；正文以用户当前确认版本为准。
10. **输出保持低压力和明确边界**：用户决定参与方式，交付类型决定输出范围；路线、正文、研究、插图、练习和发布方案分别由相应请求触发。
11. **正文围绕读者价值**：先交付明确主张、具体方案和读者能用的信息。会改变结论、选择、操作或结果的条件放在对应事实或步骤旁边，风险、合规、资格和适用性成为主题时再承担独立正文职责。
12. **传播价值来自可复述的具体判断**：先找到会改变目标读者认识、选择或行动的事实、机制或后果，再用作者自然的表达把它说清。标题、节奏和版式服务这项具体内容；可核验事实、来源、经历、数据、收益承诺和行动依据全部连接到内容真源。
13. **表达服从真实作者材料**：已有作者文本时保留其词汇、节奏、判断强度、幽默、不确定性和自然毛边，修改量与实际问题相称。具体成文、编辑与 AI 味审查标准由 `references/content-writing.md` 和 `references/content-audit.md` 承担。
14. **工作包与成品使用不同语言**：来源术语和内部字段用于核实、选择与协作；成品按目标读者重新写成人、动作、可观察变化和结果。已核实信息只有在会改变读者理解或行动时才进入成品，详细转换规则由 `references/content-writing.md` 承担。

## 任务路由

先判断主任务，只读取当前阶段需要的资源；多阶段任务随进展组合相邻流程。

| 主任务 | 何时进入 | 必读资源 |
| --- | --- | --- |
| 学习过程诊断 | 用户围绕具体材料或任务询问怎么学、为何卡住或怎样改进 | `references/learning-process-and-method-selection.md` |
| 材料提炼 | 输入是字幕、文章、课程、访谈、书摘或其他长材料 | `references/material-analysis.md` |
| 分享候选识别 | 用户要从现有材料中找适合普通受众分享的内容，并整理可交给后续制作的内容真源 | `references/shareable-content-selection.md` |
| 主题研究 | 用户只给主题，或需要主动寻找、比较和核查资料 | `references/research-led-learning.md` |
| 概念理解 | 需要解释、比较或连接关键概念 | `references/concept-deconstruction.md` |

| 研究写作 | 把研究、实践或真实经历变成内容路线、文章、修改或声音分析 | `references/article-from-practice.md` |
| 内容审计 | 检查文章是否成立、发布前重要问题，或明确要求事实审计 | `references/content-audit.md` |
| GitHub 项目短内容 | 用户要根据 GitHub 仓库、官方项目介绍、源码研究结果或已确认的项目信息写简短介绍，或者继续写同一项目系列 | `references/github-project-short-content.md`、`references/content-writing.md` |
| 平台内容组合 | 用户要面向指定平台的帖子、Thread、多条差异化短内容或带 CTA 的发布级文字包 | `references/social-content-distribution.md`、`references/content-writing.md` |
| 内容成文与改写 | 用户已授权起草或改写独立短帖、Thread、短文案、文章或 Newsletter | `references/content-writing.md`、`references/content-case-retrieval.md` |

从长材料中识别分享候选时，同时读取 `references/material-analysis.md`，先确认材料全局、真实位置和片段边界，再按普通受众的理解与传播价值筛选；用户已经指定候选时只补读取保证原意所需的上下文。通用的单条独立短内容从确认的内容真源进入成文；指定平台、多条差异化内容、发布规则或资源 CTA 会改变结果时，先按 `references/social-content-distribution.md` 建立并校验唯一 `distribution_plan`，再进入成文。用户要求文章或 Newsletter 时再读取 `references/article-from-practice.md`；用户要求具体媒体方案或制作时，先完成内容真源交接包，再交给 `visual-multimedia`。主题研究需要讲清概念时同时读取概念拆解；材料提炼需要让用户理解技术内容时也读取 `references/concept-deconstruction.md`；事实审计需要外部核查时同时读取研究流程；写作需要持久化时再读取知识库流程。

用户授权实际起草或改写独立短帖、Thread、短文案、文章与 Newsletter 时读取 `references/content-writing.md`，由当前 Agent 直接完成。GitHub 项目短介绍同时读取其专项 reference；指定平台和内容组合先建立并校验唯一 `distribution_plan`。逐字引用、数据标签、来源名称和用户明确要求保持原样的文字直接传递。外部模型只在用户本轮明确点名时使用。

通用处理顺序：

1. 确定用途、交付物、版本、授权范围和足够深度；只有方法选择需要时才判断目标表现、信息性质、已有知识和卡点。技术材料仍保留正式层，已有基础只改变可理解层的起点和展开量。
2. 用户给材料时确认正文边界、真实主题，以及关键知识是否依赖附件中缺失的板书、图表、公式或演示。用户要观看、分享或定位某种媒体时，另外核对实际分集、版本和可访问链接，并把字幕或讲义保留为分析来源。分享候选默认受众是没有专业背景的普通人；受众或来源版本会实质改变候选时再补充确认。整份材料是范围单位时，同时列出承载主线的核心知识单元。
3. 按上表读取主任务资源；组合任务只增加当前阶段确实需要的 reference。
4. 研究、解释或研究型写作在主题明确且 `System Knowledge/Home.md` 存在时先检索已有知识，再只为缺口、冲突、过时内容和关键核查补外部资料。GitHub 项目短介绍按专项来源顺序取得足够成文的事实集后直接继续；项目比较、实现机制、维护状态和实际效果由用户点名时进入相应研究深度。
5. 把材料重组成最小知识模型、解释链、分享候选、项目短介绍事实集、实践映射或真实经历主线。整份材料的学习交付覆盖核心知识单元；分享候选比较独立可懂性、实际价值、停留理由和语境完整性；项目短介绍明确项目角色、用户结果、主要能力、项目关系、事实强度和项目入口。具体媒体载体由媒体制作流程选择。
6. 用户授权独立短内容、文章或 Newsletter 成文时，按 `references/content-writing.md` 建立唯一写作输入：`writing_job` 保存对象、角度、交付形态、受众、核心信息和当前全部要求；`content_truth` 保存事实与来源；`author_voice` 保存真实作者来源、声音信号和明确保留的表达选择；`writing_templates` 与 `writing_examples` 保存当前生产者实际读取的对应模板和同类型完整案例。短内容读取完整 `short`，文章或 Newsletter 读取完整 `article`，病毒式传播任务再读取 `hook`。GitHub 项目短介绍使用 `github_project_short` 交付形态，并把项目事实、用户结果、主要能力、入口、系列关系和呈现合同写入 `github_project`。四类资源通过 `validate-writing` 后成为本轮正文的唯一输入。平台内容组合先生成并通过 Harness 校验 `distribution_plan`。这些英文键名和过程标签只服务内部协作，当前 Agent 按目标读者重新成文。
7. 初稿完成后阅读全文，先保留有作者特征、信息明确且读起来顺的句子，再做最小有效修改：让具体的人或事承担动作，用事实、机制、数字和例子替代空泛的重要性表述，处理重复、难懂结构和失去作用的铺垫。段落长短、停顿和完成度跟随作者材料与内容需要。用户反馈作为当前任务合同的增量，只改变其实际点名的层级；修改稿继续按合并后的完整任务合同验收。用户纠正声音时回到真实作者文本重做取舍。
8. 得到写入授权且形成稳定增量时，通过 Harness 校验后合并到唯一真源。写入前用范围单位做一次覆盖核对：整份材料中的每个核心知识单元进入能够独立呈现全局结构的综合主题文档，或进入被综合主题明确连接的专题文档；追问中确认的解释修正、关键反例、应用边界和必要外部核查合并到对应层。来源记录负责证明材料内容，知识文档负责呈现已经整理的知识。当前授权范围决定是否写入。
9. 达到当前用途、授权和保存位置要求后停止。

## 跨流程边界

### 分享候选交接

分享候选确认后，为每项整理核心主张、普通受众价值、必要语境、支撑材料、来源位置、事实与版权状态和可用素材。个人或系列内容同时交接经过确认的作者判断、真实作者来源和当前声音信号。同一来源将派生多个成品或当前任务属于连续系列时，再记录稳定的来源标识、来源版本和内容单元标识；下游每个媒体项目沿用这组来源信息并建立自己的项目与成品记录。用户只要求找内容时交付这些字段后停止；通用单条短内容由当前 Agent 直接成文；平台化或多条分发请求先把交接包转成唯一 `distribution_plan`，通过结构校验后再成文；文章或 Newsletter 进入文章流程；具体媒体方案或成品把选定内容、认知锚点和内容真源交给 `visual-multimedia`。

### GitHub 项目短内容

GitHub 项目短介绍以项目官方仓库、用户提供的本地项目材料或当前对话中已经确认的项目研究结果为事实来源。专项流程先建立项目角色、用户结果、主要能力、事实强度、项目入口和系列关系，再把活动呈现合同写入 `github_project.presentation`。基础成文模板、专项模板、“项目与产品介绍”完整案例、当前作者声音和内容真源共同进入 `validate-writing` 的活动写作包。用户明确要求病毒式传播时再加入开头案例。用户只要求短介绍时交付正文与项目入口后停止；指定平台、多条差异化内容或 CTA 时转入平台内容组合。

### 知识库

本地知识库固定为 `System Knowledge`，目录和文档规则以 `System Knowledge/Home.md` 为准。该文件存在时进入本地检索；交付必须持久化且文件缺失时询问真实位置。

用户明确要求保存或更新、交付物本身是文件，或当前项目规则明确要求回写时进入写入分支。长期复用价值决定写什么；获得授权后把稳定增量合并到唯一真源。

### 写作、声音与内容审计

内容路线、结构、起草、修改、声音分析、内容审计、逐字校对、研究和事实核查分别按用户要求组合。个人经历型文章以用户提供或确认的真实经历为骨架；研究解释型文章从主题知识和证据进入。缺少会改变主体的经历节点时只询问该缺口。

用户只要求判断 AI 味或模板感时，按 `references/content-audit.md` 进入检测模式：引用最能说明问题的原句，命名可观察模式，说明影响和最小修法后停止。用户同时要求修改时，再按 `references/content-writing.md` 做最小有效编辑。

进入声音分析或个人经历起草前，先验证样稿的作者身份和状态。同一文章同时存在 Agent 草稿、用户改稿、确认稿或已发布版本时，使用用户指定或确认程度最高的版本；“最新”指经过验证的当前有效版本。外部参考作者只提供可迁移的主张、结构、事实和表达机制，不提供用户身份、亲历或立场。

用户可以用简短指令 `文章模式：<主题>` 进入完整的研究写作交付。它默认表示：读取相关旧文、项目和声音材料，研究成文必需的缺口，生成“写作大纲＋具体参考内容”，并保存为 Markdown 文件。用户明确说“写文章”且要求“大纲和具体参考内容”时，与该指令同义。

文件位置已能从现有文章、系列项目或 `System Knowledge/Home.md` 推断时直接落位。大纲、参考正文、Agent 草稿和用户尚未确认的改稿属于过程材料：优先更新现有项目草稿，其次在 `System Knowledge/30-Projects/Content` 建立唯一文章项目并保存。用户确认成稿或提供已发布版本后，把唯一成果迁移到 `System Knowledge/40-Outputs/Writing/Articles`，同步更新项目状态和全部活动链接。现有规则无法确定项目或成果位置时再询问路径。

用户要求延续个人风格或已经提供样稿时，读取经过作者身份与状态验证的当前有效用户样稿；`System Knowledge/60-Systems/Writing/style-guide/voice.md` 存在时再读取该唯一声音真源，并以当前指令和当前有效用户样稿为最高优先级。内容审计默认使用用户提供的正文和材料，报告阻断和实质问题；事实审计与逐字校对按单独授权进入。

用户选择把分享候选发展为长文或 Newsletter，并明确要求实际起草时，按本节和 `references/article-from-practice.md` 处理文章承诺、声音、材料、交付粒度和保存位置。

### 实践

实践开始前确定目标产物、成功标准、真实环境、可用资源、执行规模、观察指标和交付位置。成功标准保持稳定，再简化用户操作负担；执行后用同一标准检查结果。

## 输出与停止

输出随请求变化：

- 概念问题先直接回答核心，再按需要补机制、情境和关键边界。
- 抽象、技术或公式密集的概念与材料先交付可理解层，再交付正式层。可理解层说清“是什么、做什么、怎样判断”，并让核心概念经过一个完整情境；正式层保留当前主题必要的精确结构。
- 普通人行动总结、最终清单或“实际怎么用”部分使用已解释的普通语言；定义、公式和高阶关系进入其后的独立正式层。
- 用户点名视频、原始发布版本、具体分集、时间位置或网页链接时，直接提供对应媒体的实际入口和定位信息；讲义、字幕、搜索摘要和本地知识库路径作为分析依据。
- 分享候选先给按推荐顺序排列的结果。每项至少说明真实位置、完整意思、普通受众为什么值得看、停留理由、必要语境、支撑材料、来源与版权状态和可用素材；具体媒体形式留给媒体流程。
- 用户授权的独立短帖、Thread、短文案、文章和 Newsletter 由当前 Agent 直接生成；开头从最早能够承载具体内容或必要个人语境的句子开始。
- GitHub 项目短介绍先用一句有独立措辞的开头建立兴趣，再说明项目为谁解决什么问题，正文只保留普通读者能理解的高价值能力，并用经过确认的项目入口收束；同一系列同时交代项目关系并保持活动呈现合同一致。
- 独立文字成品用作者真实的词汇、节奏和判断强度交付核心信息，具体事实与机制保持原有精度；已经自然有力的句子保持原样，修改集中在确实妨碍内容与声音的部分。
- 平台内容组合先交付 `distribution_plan` 中约定的全部正文和对应 CTA，再补充会影响发布的当前平台规则、链接缺口或热点来源；内部计划只在用户要求时展示。
- 内容分发的全局扫描用于比较候选，交付停在候选与内容真源；讲解任务另行进入两层解释。
- 判断现实对象是否符合某个数学概念时，先给有边界的直接结论，再说明观察对象与状态怎样定义、模型作了什么假设、现实证据支持什么。
- 研究先交付当前用途需要的知识模型、证据和未知；知识库修改由写入授权触发。
- 长材料先给主线和最值得看的内容；是否继续解释、核查或实践由请求决定。
- 用户要求看完整材料时，主线覆盖全部核心知识单元；用户只问单个概念时，回答和后续沉淀停在该概念及其必要关系。
- 学习诊断先说明当前卡点及依据，再给最小方法和可观察结果；长期计划由用户请求触发。
- 内容路线具体到能够继续写，文章按约定的写作动作交付。
- `文章模式` 或“写文章＋大纲和具体参考内容”直接交付位于文章项目中的 Markdown 文件；用户确认或已有发布版本时交付 `40-Outputs` 中的最终成果。第一段先给成文方向或文件结果。

资料已经支持当前交付、关键未知已经标明、授权内的事实与保存位置已经处理时停止。分享候选完成排序、定位、语境检查和内容真源交接包时停止；独立短内容、文章和 Newsletter 由明确的成文请求触发，上传和发布由对应授权触发。更深层启示、风险教育、练习、标题、插图、额外平台版本和运营方案分别由用户需求触发。

## 工具与确定性门禁

简单回答直接完成。以下情况使用 `harness`：

| 场景 | 命令 |
| --- | --- |
| 复杂任务跨越研究、实践、写作或持久化 | `python -m harness validate-task -` |
| 准备内容路线、结构、草稿或修改稿 | `python -m harness validate-writing -`；同一个写作包必须包含内容真源、作者声音、对应模板和同类型完整案例 |
| 交付内容审计 | `python -m harness validate-audit -` |
| 写入知识库前 | `python -m harness validate-write -` |
| 新建或更新主题知识文档后 | `python -m harness validate-note "文档路径"` |
| 使用高影响事实、实时事实或精确引语 | `python -m harness validate-evidence -` |
| 指定平台、多条差异化内容或带 CTA 的发布级文字包 | 按 `references/social-content-distribution.md` 形成计划，再运行 `python -m harness validate-distribution -` |
| GitHub 项目短介绍 | 按 `references/github-project-short-content.md` 形成事实集与呈现合同，再由当前 Agent 直接成文 |
| 起草或改写独立短内容、文章与 Newsletter | 按 `references/content-writing.md` 同时准备内容真源、当前作者声音、对应模板和同类型完整案例，再由当前 Agent 直接成文 |

校验失败时修正同一任务合同、输入、审计结果、证据包或目标文档。JSON 字段与允许值以 `harness/policies.py` 为准；作者声音由当前样稿对比和人工阅读判断。

本地 SRT、VTT、带时间戳 TXT 或断行严重的字幕需要规范化时，运行 `scripts/normalize_subtitles.py`。保留原文件和真实时间位置；格式无法识别时说明格式并人工分段。

修改本 Skill、reference、Harness 或脚本后运行：

```powershell
python -m harness doctor
python -m unittest discover -s tests -v
```

触发边界、研究深度、写作输出或质量标准发生变化时，在当前任务中临时选择至少两个表面不同、但依赖同一机制的普通请求，逐项推演开始判断、允许来源与动作、输出开头、交付载体和停止位置。临时推演留在当前任务；长期测试验证结构、合同字段和与案例措辞无关的明确不变量。

## 交付前检查

- 当前交付、深度、用途和停止位置一致。
- GitHub 项目短介绍已经确认项目身份、官方或既有事实来源、用户结果、事实强度、项目入口、系列关系和活动呈现合同；`github_project_short` 写作包同时包含基础模板、专项模板、“项目与产品介绍”完整案例、作者声音和内容真源。
- 写作包字段、来源实现说法和案例检索标签只留在内部；成品已经把选中的含义写成目标读者熟悉的动作、变化和结果。
- 技术内容先用具体情境建立可理解层，再保留必要的正式定义、公式、条件和关系。
- 用户点名的媒体载体、版本和位置已经直接交付。
- 分享候选适合目标受众独立理解和受益，并具备真实位置、完整语境、内容真源与版权状态。
- 独立文字成品及其修订由当前 Agent 直接完成；外部模型只在用户本轮明确点名时使用，媒体成品由 `visual-multimedia` 接续。
- 平台内容组合的读者、内容原子、帖子任务、平台核查、热点和 CTA 只有一个活动 `distribution_plan`；计划通过门禁并被同一写作内容包消费。
- 学习方法对应目标表现、已有知识和真实卡点，并有可观察结果与停止条件。
- 材料、来源、证据、案例、推断、素材和个人观点角色清楚，重要结论连接原文或合适证据。
- 实践承接本次学习或研究，并覆盖成功标准、真实资源、执行规模和观察指标。
- 写作对象、请求角度、核心信息和授权已经确认；第一人称经历来自用户材料，外部案例没有被改写成用户亲历，辅助事实没有取代用户要求的主线。
- 内容路线、文章结构、首次草稿和修改稿已经按写作任务、内容类型、主题、结构与交付形态读取本地完整案例；短内容读取 `short`，文章读取 `article`，病毒式传播任务再读取 `hook`。
- 多轮修订以当前有效正文和当前全部要求为唯一真源；成稿仍能观察到所有未被撤回的要求。
- 事件型短内容已经形成目标读者需要的事件闭环；时间线和研究细节只在它们承载主线时进入正文。
- 每次成文的作者声音来源和一至五项声音信号能够回到用户本轮原话、当前有效正文、确认稿、已发布内容或维护中的声音档案。
- 吸引人或病毒式传播内容存在一个由事实、机制或后果支撑的具体判断，读者可以准确复述。
- 修改保留了已经自然有力的句子、节奏变化和必要个人语境，改动量与实际问题相称。
- 内容包中的对象、核心信息、当前全部要求、作者声音、模板和完整案例共同进入同一个生产输入。
- 多条平台内容在任务、角度、主要内容原子、开头策略和互动方式上形成可观察差异，每项事实仍能回到内容真源。
- 知识库写入、文章项目和最终成果各自进入唯一真源并通过对应 Harness。
