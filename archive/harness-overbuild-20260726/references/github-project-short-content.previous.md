# GitHub 项目短内容

<!-- 旧写作包与案例强制流程，已退出活动 Skill。 -->

用于把 GitHub 项目的官方介绍、用户提供的本地材料或已经确认的项目研究结果，写成普通读者能独立看懂、愿意转述并继续了解的简短介绍。本文件是专项模板；成文时与基础成文模板、同类型完整短内容案例、当前作者声音和项目事实同时使用。

## 一、进入条件与停止位置

用户要求介绍、推荐、分享或续写一个 GitHub 项目，并且交付物是一条简短文字时进入。默认目标是让普通读者迅速知道项目带来什么结果、怎样做到以及从哪里访问。

用户要求完整项目研究、实现机制、亲自运行、维护状态、项目比较或实际效果时，先按相应研究流程形成内容真源；随后需要短内容时再进入本流程。用户指定平台、多条内容、Thread、热点或 CTA 时，同时读取 social-content-distribution.md。

正文已经完成项目介绍的内容职责，项目入口和用户要求的结尾已经交付，正文事实都能回到内容真源时停止。

## 二、建立项目事实集

按顺序读取：

1. 当前对话中已经确认的项目研究结果和用户提供的本地材料。
2. 官方 GitHub 仓库的 README、文档和能够直接核对的实现。
3. 官方项目站、论文或模型页中与当前介绍直接相关的补充说明。
4. 用户明确要求当前版本、热度、维护状态或外部评价时，再读取相应当前来源。

内容真源至少回答：

- 谁会使用这个项目，原来在做什么。
- 用户给它什么输入或操作，最后得到什么。
- 哪些少量能力真正支撑这个结果。
- 项目在完整工作流中承担什么角色。
- 项目入口以及会实际改变目标读者选择的使用条件。

事实状态使用 direct、project_claim、observed 和 unconfirmed。功能、输入输出和兼容环境由官方材料支持时可以直接陈述；速度、质量和领先程度保留项目方声明身份；本轮真实运行看到的结果标记为观察；来源不足的内容留待确认。

热度、许可证、核对日期、技术栈、费用、外部服务和维护状态根据读者价值选择。用户点名这些信息，或它们会改变目标读者是否点击、安装或使用时，把它们加入正文职责；其它已核实事实继续留在 content_truth。

## 三、确定唯一主任务

短介绍先写清：

~~~text
目标读者：
读者原来要完成什么：
项目怎样改变这件事：
最值得转述的具体结果：
作者怎样判断项目的角色：
读完后的下一步：
~~~

同一系列继续介绍另一个项目时，再写清前一项目与当前项目分别承担什么角色、两者怎样配合或替代，以及本条新增的用户价值。新正文独立成立，同时让读过前文的人知道它在系列中的位置。

## 四、专项模板的内容职责

这类正文依次完成五项职责，实际段落数量和顺序根据当前作者声音与完整案例调整：

1. **让结果出现**：第一段出现项目带来的具体结果、可见变化或真正值得转述的判断。
2. **说清操作**：用普通读者熟悉的动作说明用户给项目什么，它连续做了什么，最终交付什么。
3. **选择能力**：使用二至四项最能支撑结果的能力，写成行动者、动作和结果。
4. **给出作者判断**：事实讲清后，由作者概括项目在当前场景中的角色。这个判断可以鲜明、口语、粗粝，也可以使用已经由正文证明的比喻。
5. **完成入口与收束**：按用户要求安排项目链接、固定结尾、下一步或自然余味。

实现名、文件夹、框架和参数先帮助 Agent 还原项目怎样工作。正文把它们转换成用户能看到或做到的动作；精确术语确实影响理解时保留并当场说明。

## 五、同时使用完整案例和作者声音

GitHub 项目短介绍固定读取：

- references/content-writing.md。
- references/github-project-short-content.md。
- 至少一条内容类型为“项目与产品介绍”的完整 short 案例。
- 当前用户原话、当前有效正文或经过确认的作者文字。

用户明确要求病毒式传播时，在完整项目介绍案例之外再读取 hook 案例。完整 short 案例展示一条项目介绍怎样从开头走到结尾；hook 只补充开头的注意力方式。

模板和完整案例同时进入同一个写作输入。模板负责内容职责，案例负责展示职责怎样变成自然正文，作者材料负责用词、句长、重复、判断力度、幽默和完成度。当前项目事实替换案例事实；生产者保留案例的整体推进和节奏，不把案例压缩成几个写作技巧后再凭空生成。

## 六、正面安排传播与判断

根据项目材料选择入口：

- 项目最强的是完整结果时，从最小输入写到最终产物。
- 项目改变了繁琐操作时，先写原来真实存在的步骤或代价，再写现在发生的变化。
- 项目修正目标读者的常见理解时，先把该理解放在具体场景中，再用项目事实说明变化。
- 项目能力很多时，用一条真实操作流程把它们串起来，让读者看见项目怎样连续工作。
- 项目角色已经由前文事实证明时，用作者自己的判断把它压成一句容易记住的话。

比喻、抬升和鲜明判断放在事实已经足以支撑的位置。用户明确保留的称呼、重复、口语和结尾进入 author_voice.preserved_choices，当前正文沿用这些选择。

## 七、形成唯一写作输入

writing_job.deliverable 使用 github_project_short。writing_templates 同时包含基础成文模板与本专项模板。writing_examples.content_type 使用“项目与产品介绍”，references 至少包含一条完整 short 案例；病毒式传播任务再包含 hook 案例。

github_project 保存：

~~~text
项目名与入口
目标读者与原问题
用户最终结果
项目在工作流中的角色
支撑结果的主要能力
系列关系
开头任务、正文形态、链接位置和结尾任务
~~~

content_truth 保存项目事实和来源，author_voice 保存当前作者材料、声音信号和明确保留的表达选择。四项资源通过 validate-writing 后，当前 Agent 直接成文。

## 八、交付前验收

1. 第一段已经让普通读者看见具体结果、变化或值得转述的判断。
2. 正文让读者知道谁使用项目、给它什么、它做什么以及最后得到什么。
3. 每项能力都支撑主结果，项目介绍形成一条连贯流程或判断。
4. 作者声音能够回到真实用户材料，明确保留的称呼、重复和结尾继续生效。
5. 专项模板与“项目与产品介绍”完整案例同时进入生产输入；病毒式传播任务同时读取开头案例。
6. 作者判断和比喻由前文事实支撑，结尾完成项目入口、下一步或用户要求的收束。
7. 进入正文的热度、许可证、费用、技术栈和使用条件确实承担当前读者需要的信息职责。
8. 公开正文使用目标读者熟悉的动作与结果，内部字段和 README 分类只留在工作包。
9. 正文独立成立并达到短介绍用途后停止。
