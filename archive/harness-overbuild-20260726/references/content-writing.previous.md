# 内容成文

<!-- 旧写作包与案例强制流程，已退出活动 Skill。 -->

用于把已经整理并核实的内容写成独立短帖、GitHub 项目短介绍、Thread、短文案、文章或 Newsletter。当前 Agent 直接完成起草和修改，并对最终文字负责。

## 一、进入条件与唯一生产链

用户已经授权起草、改写、扩写、压缩或重组独立文字时读取本文件。分享候选识别、研究、事实核查、内容审计和知识讲解继续走各自主路径；卡片、视频、音频与媒体成品共同设计的文字交给 visual-multimedia。

所有成文动作使用同一条生产链：

~~~text
内容真源 + 当前作者声音 + 对应写作模板 + 同类型完整案例
→ 同一个写作输入
→ 当前 Agent 直接成文
→ 对照作者声音、模板职责和案例机制阅读全文
→ 交付当前唯一正文
~~~

这四项在起草、结构调整和文字修改时同时存在。模板保证正文完成该类内容的职责；同类型完整案例展示开头、推进、密度、节奏和收束怎样真正连在一起；当前用户文字、确认稿和声音档案决定用词、句长、重复、判断强度、幽默与自然毛边；内容真源决定事实、经历、数字和能够成立的结论。

每条可分享内容都要给读者继续看、记住或转述的理由。用户明确要求病毒式传播时，viral_requested 记录这项额外要求，并在完整正文案例之外同时读取开头案例。它只增加传播强度和开头参考，不建立另一套写作模式。

## 二、建立当前唯一写作任务

成文前确认：

- **对象与角度**：正文具体讲什么，从用户要求的哪个角度讲。
- **读者与用途**：谁会读，读完需要理解、记住、判断或采取什么动作。
- **核心信息**：按重要性排列的事实、经历、机制、结果和作者判断。
- **当前要求**：用户仍然有效的长度、平台、固定文字、措辞偏好和其它要求。
- **交付形态**：short_post、thread、short_copy、github_project_short、article 或 newsletter。
- **推进依据**：真实经历时间线、问题逐步推进或研究解释。

writing_job.requirements 是本轮全部有效要求的唯一真源。首次起草直接写入当前要求；用户继续修改时，以当前有效正文和最新反馈重建这份列表，保留仍然有效的要求，替换已经改变的部分。修改动作同时用 current_text_reference 指向当前有效正文，不维护另一套版本账本。

content_truth 保存能够进入正文的具体陈述、状态和来源。公开正文从中选择真正推动读者理解、判断或行动的信息。许可证、费用、维护状态、核对日期、技术栈、风险和适用条件在它们本身是主题，或会实际改变目标读者选择时进入正文；其余信息继续留在内容真源中。

## 三、同时读取模板与完整案例

模板路径按交付形态确定：

- 通用短帖和短文案：references/content-writing.md。
- Thread：references/content-writing.md 与 references/social-content-distribution.md。
- GitHub 项目短介绍：references/content-writing.md 与 references/github-project-short-content.md。
- 文章和 Newsletter：references/content-writing.md 与 references/article-from-practice.md。

随后读取 references/content-case-retrieval.md，按写作任务、内容类型、主题和结构取得完整案例：

- 短帖、Thread、短文案和 GitHub 项目短介绍读取至少一条同内容类型的 short 全文。
- 文章与 Newsletter 读取至少一篇同内容类型的 article 全文。
- viral_requested=true 时，在对应正文全文之外再读取至少一条 hook。
- 起草和修改都使用当前任务对应的模板与案例；对象、交付形态、内容类型或整篇推进变化时重新检索。

选中的模板进入 writing_templates，完整案例路径进入 writing_examples.references。当前 Agent 直接读取完整资源并与内容真源、作者声音同时成文。案例全文承担示范作用，不先压缩成“痛点翻转”“反常识”或其它抽象标签；这些名称只帮助理解案例为何有效，不能代替完整推进和节奏。

Thread 和其它已经进入平台内容组合流程的成文任务，把通过校验的 distribution_plan 原样放入同一个写作输入。它负责平台、条数、内容差异、互动和 CTA；模板、完整案例、作者声音与内容真源继续负责实际正文。

## 四、让作者声音始终进入正文

每次成文都建立 author_voice。来源优先级是：

~~~text
用户本轮原话与明确反馈
→ 当前有效用户正文或确认稿
→ 已发布作者内容
→ 维护中的唯一声音档案
~~~

至少保留一项用户来源，并从本轮真正相关的材料中提取一至五项可观察信号，例如：

- 用户常用的词、指代和判断力度。
- 句子长短、停顿、重复和段落密度。
- 幽默、夸张、直白、自我修正或自然毛边怎样出现。
- 作者怎样从事实走到判断，又在什么位置结束。
- 本轮已经明确保留的原句、称呼、重复或收束方式。

author_voice.signals 写当前最有用的声音信号，preserved_choices 写用户明确保留的表达选择。它们帮助生产者关注作者特点，真实来源全文仍然是声音依据。用户确认某个称呼、自然重复、判断力度或逐字结尾时，这些选择直接进入当前写作输入。

第一人称经历来自用户当前输入、确认稿或已发布文章，并在 experience_events 中保留来源。研究材料、外部案例和 Agent 草稿负责事实、结构或待修改文本，不提供用户亲历。

## 五、正面使用传播技巧

传播技巧由当前材料触发，作用是让具体内容更快成立：

- **结果钩子**：从内容真源选择普通读者最容易看懂、最想复述的具体结果，第一句直接让这个结果出现。
- **痛点翻转**：先写用户原来要做的具体动作、花费或阻力，再写项目或方法带来的可见变化；前后两端都由材料支撑。
- **反常识入口**：先找到目标读者真实持有的常见理解，再用当前材料中的新事实或机制修正它。
- **问题入口**：提出正文能够立即回答、且目标读者确实关心的问题，后续段落持续兑现这个问题。
- **二元抬升**：事实和能力已经讲清后，用作者自己的判断概括对象在当前场景中的新角色。
- **比喻与记忆点**：把正文已经证明的多项能力压成一个容易记住的形象，让它总结事实。
- **结尾**：完成作者判断、读者下一步、项目入口或自然余味中的一项，让正文在该停的位置结束。

同一种技巧在不同内容中会产生不同句子，因为人物、动作、结果、判断和作者声音都来自当前输入。完整案例展示这些技巧怎样与上下文连接；当前 Agent 借用其作用和推进关系，再用本轮事实与作者语言完成新正文。

## 六、直接成文

先让最有价值的内容尽早出现，再按读者理解需要推进。每一段都加入新的事实、动作、因果、结果、作者判断或下一步，前文提出的问题在后文得到兑现。

重要句子至少完成一种实际作用：

- 提供当前对象特有的事实、动作、机制、数字或结果。
- 连接行动者、条件、变化与后果。
- 给出能够由现有材料支撑的作者判断。
- 保留当前作者真实的词汇、节奏、重复、幽默或自然毛边。
- 让核心内容更容易理解、记住或准确转述。

技术材料先还原“谁做什么、用户看到什么变化、最后得到什么”，再用目标读者熟悉的对象和动词写成正文。必要术语保留精度，并在第一次出现时说明它在当前场景中改变什么。内部字段、检索标签、README 分类和研究过程只通过选材与组织影响成品。

短句、长句、段落、列表、重复和岔开都由当前作者声音与信息关系决定。列表适合并列信息，连续段落适合过程、因果和判断；二者可以自然混合。

## 七、完成语义检查

初稿完成后，把正文与四项生产输入一起重读：

1. 开头已经出现具体对象、结果、冲突或问题，并在正文得到兑现。
2. 每一段都推动事实、因果、理解、判断或读者行动。
3. 模板规定的内容职责已经完成。
4. 完整案例中的开头作用、推进、密度、节奏或收束机制被当前材料真正承接。
5. 重要句子能回到内容真源、作者判断或作者声音。
6. 作者明确保留的措辞、重复、完成度和结尾得到保留。
7. 转折和抬升建立在前文事实之上；比喻压缩已经证明的能力。
8. 公开信息服务当前读者，事实包中的旁支信息没有抢走正文主线。
9. 全文脱离内部工作包后能够独立阅读，像同一个具体作者在讲这一件事。

这一步由当前 Agent 按语义完成。content-audit.md 在用户要求判断 AI 味或模板感时引用具体原句定位问题；Harness 只核对资源、来源、授权和结构是否进入同一个生产输入。

~~~powershell
python -m harness validate-writing writing-packet.json
~~~

## 九、GitHub 项目短介绍

GitHub 项目短介绍同时执行 github-project-short-content.md。专项模板负责项目身份、用户结果、主要能力、项目角色、入口和收束；同类型完整案例展示这些职责怎样自然组成一条短内容。

项目事实来自官方仓库、用户提供的本地材料或已经确认的项目研究结果。热度、许可证、技术栈、费用、外部服务和维护状态根据当前读者价值进入正文。用户要求的是项目能力与传播内容时，正文集中写项目实际完成的动作、结果和作者判断；用户明确询问使用条件、费用、许可或风险时，再让这些信息承担相应正文职责。

## 十、停止条件

正文满足当前写作任务、模板职责、作者声音、案例机制、内容真源和用户要求后直接交付。内部写作包、检索过程和校验标签只在用户要求时展示。
